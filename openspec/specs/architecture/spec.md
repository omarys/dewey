# Architecture Specification

> Generated by openlore v1.2.0 on 2026-10-07 15:05

## Purpose

This document describes the architectural patterns and structure of the system.

## Architecture Style

Monolithic terminal application architecture organized around modular domains (UI, App, Scanner,
Runners, Persistence) with an asynchronous event-driven core.

## Requirements

### Requirement: LayeredArchitecture

The system SHALL maintain separation between:
- User Interface (UI) (Manages terminal lifecycle, screen buffering, input flushing, widget layouts, and theming for interactive TUI displays.)
- Application & Orchestration (Maintains central application state, dispatches asynchronous terminal events and timer ticks, and orchestrates user workflows.)
- Scanner & Maintenance (Discovers local library files, parses chapter/series metadata, standardizes naming conventions, and reconciles filesystem changes with the database.)
- External Process Runners (Encapsulates subprocess spawning, command construction, and exit payload parsing for external reader and querying tools.)
- Persistence (Provides persistent storage and querying for Series, Chapter, and Progress entities via SQLite, supported by local JSON history caching.)

#### Scenario: LayerSeparation
- **GIVEN** a request from the presentation layer
- **WHEN** business logic is needed
- **THEN** the presentation layer delegates to the business layer
- **AND** direct database access from presentation is prohibited

### Requirement: SecurityModel

The system SHALL implement security via: No formal authentication or authorization model is implemented or required; security relies entirely on local operating system process privileges and host filesystem permissions.

#### Scenario: AuthenticatedAccess
- **GIVEN** an unauthenticated request
- **WHEN** accessing protected resources
- **THEN** access is denied

## Layer Structure

### User Interface (UI)

**Purpose**: Manages terminal lifecycle, screen buffering, input flushing, widget layouts, and theming for interactive TUI displays.
**Location**: `src/ui/mod.rs, src/ui/components.rs, TuiService, UiRenderer, UIComponents, ThemeService`

### Application & Orchestration

**Purpose**: Maintains central application state, dispatches asynchronous terminal events and timer ticks, and orchestrates user workflows.
**Location**: `src/main.rs, src/app.rs, App, EventHandler`

### Scanner & Maintenance

**Purpose**: Discovers local library files, parses chapter/series metadata, standardizes naming conventions, and reconciles filesystem changes with the database.
**Location**: `src/scanner.rs, scripts/standardize_library_names.py, LibraryScanner, StandardizeLibraryNamesService`

### External Process Runners

**Purpose**: Encapsulates subprocess spawning, command construction, and exit payload parsing for external reader and querying tools.
**Location**: `ContinuumRunner, LabradorRunner`

### Persistence

**Purpose**: Provides persistent storage and querying for Series, Chapter, and Progress entities via SQLite, supported by local JSON history caching.
**Location**: `src/db/mod.rs, Database, DebugHistory`

## Data Flow

Filesystem scan or terminal user event → EventHandler/LibraryScanner updates App state → Database
layer writes/reads Series, Chapter, and Progress records in SQLite (with DebugHistory JSON fallback)
→ ContinuumRunner or LabradorRunner executes external CLI tools to view chapters or retrieve
metadata → Exit payloads capture updated progress back into the database and UI.
